# Phase 3 acceptance checklist - admin application

Rules for using this file (same as Phase 1 and 2):

- An item is done only when its proving test exists, passes, and is named in the "Proof" column. "It works when I run it" is not proof.
- Work top to bottom within a group; groups are ordered by dependency.
- When all items in a group are proven, commit with message `phase3: <group> complete`.
- Do not edit the criteria to match the implementation. If a criterion is wrong, raise it with the lead first.
- Each group gets its own working session: research any new dependency/API empirically before designing, a plan-mode design review for anything with a real architectural decision, then implement in small commits.

This is a first-pass draft, written before any admin code exists. Unlike Phase 1/2's checklists (refined session by session against a codebase that already existed one phase earlier), several criteria here will firm up - or change - once their own group's design session actually researches the chosen tooling. That is expected, not a sign the draft was wrong; each group should feel free to revise its own not-yet-started rows before implementing them, same as any other group would flag a wrong criterion to the lead.

The admin lives in its own repository (`app-granite-cms-admin`, sibling to this one, empty at the time of writing), per the build plan's constraint that the admin and the site are always two separate codebases with two separate deploy cycles. This checklist stays here, alongside the build plan it's derived from, matching where Phase 1 and 2's checklists already live.

## Open questions carried in from scoping (resolve at the named session, not before)

1. ~~Admin persistence mechanism~~ **Resolved in Group A: a JSON-file-backed `Store<T>` interface** (`packages/server/src/store/` in the admin repo). Not modelled on this repo's own SQLite driver-interface precedent - that exists because a second real implementation (`better-sqlite3`) already exists and the data (the search index) is disposable/rebuildable; neither is true of the admin's registry/account data, which is small-volume and authoritative. The interface's real job is testability (an in-memory fake for later groups' route tests), with "could swap to SQLite later" as a true but secondary bonus - so no grep-enforced single-implementation test was added, unlike this repo's B7/G5 precedent. Atomic writes (temp file + rename) and a promise-chain write-queue mutex are built in from day one, since this data is authoritative, not derived.
2. ~~Admin login mechanism~~ **Resolved in Group B: username/password against the Store-backed users collection.** No OAuth/magic-link - matches the self-hosted/free-tier simplicity bias, and SSO is explicitly an Enterprise-tier feature for later (per the commercialisation strategy), not something to build speculatively into Phase 3. Hashed with `node:crypto`'s `scrypt` + `timingSafeEqual`, no new dependency.
3. ~~Session mechanism~~ **Resolved in Group B: real server-side sessions** (`@fastify/session` + `@fastify/cookie`, backed by the admin's own `Store<T>` via a small callback-adapter), not a stateless signed cookie - chosen for genuine server-side revocation on logout, confirmed directly with the user against the alternative's lower cost (one dependency instead of two, no server-side store).
4. ~~Test tooling for the admin repo~~ **Resolved in Group A: a split, not a preference.** `node --experimental-strip-types --test` (matching this repo exactly) for the admin's backend, but Vitest + React Testing Library + jsdom for frontend component tests - forced, not chosen: `--experimental-strip-types` only erases type annotations, it does not transform JSX, so a `.tsx` file cannot run under bare `node:test` at all. Real end-to-end browser tests (mirroring this repo's `page-reviewer` precedent) remain undecided and deferred - no group has needed one yet.
5. Diff rendering for the history view (Group H): a real diff needs a real diffing library (line-level, at minimum) - which one, and how much of a merge-request-style UI it justifies, is a Group H research question, not decided here.

Design notes:

- **The admin gets its own lightweight Node backend (Fastify), not a pure browser SPA** - a real architectural gap in the original build plan, caught before any code was written: it only sketched frontend folders, but a shared, multi-user site registry holding real secrets (per-site API tokens) and real login sessions can't safely be browser-only storage. The backend proxies every site call, so a registered site's raw API token never has to reach the browser at all - confirmed directly with the user rather than assumed, given a genuine alternative (a third-party auth/BaaS provider) existed and was rejected as introducing an external vendor dependency for a tool whose whole pitch is "own your stack."
- **Two npm workspace packages (`packages/server`, `packages/web`), one repo** - a real split, not premature structure: Node/NodeNext and browser/bundler-resolution-with-JSX are genuinely different compilation targets with different dependency sets.
- **A real CVE caught before it shipped, not by inspection**: the first pass pinned `@fastify/static` at `^8.1.0` (matching what was available when the plan was drafted); `npm audit` immediately flagged four high-severity path-traversal/route-guard-bypass advisories against 8.x/9.x. Re-pinned to `^10.1.2` (confirmed via `npm view` to have no peer-dependency conflict with Fastify 5) before writing any code against it - path/traversal safety is treated with the same seriousness here as the agent repo's own `sanitisePath`.
- **`@vitejs/plugin-react`'s Babel variant, not the SWC variant** - the SWC variant ships a native Rust binary, the same "native module pain" this project already steered around by choosing `node:sqlite` over `better-sqlite3`.
- **The built web assets' default location is resolved from the server module's own location (`import.meta.dirname`), not `process.cwd()`** - deliberately the opposite convention from the agent's own "never resolve relative to the package location" rule (constraint 2 there), because the two situations aren't the same: locating a *fixed sibling build artifact* (`packages/web/dist`, always two directories under `packages/` from either source or compiled `packages/server/{src,dist}`) is a structural fact independent of deployment, unlike the agent's site *content*, which is genuinely external, per-deployment configuration. The admin's own data directory (site registry, accounts) stays `process.cwd()`/`ADMIN_DATA_DIR`-relative, since that genuinely is operator configuration - the two defaults are deliberately resolved differently, for different reasons, not an inconsistency.
- **A real port collision caught by actually running it, not by inspection**: the default dev port (originally 4000) turned out to already be bound by an unrelated pre-existing local process on the development machine. Moved to 4278 after verifying the dev-mode Vite-proxy-to-Fastify wiring end to end with real requests.
- **Stop-gate hooks are per-project and were ported, not inherited** - `app-granite-cms-admin` has its own `.claude/settings.json`/`.claude/hooks/`, adapted from this repo's (the staleness check's `find` glob changed from a flat `src test` to `packages/*/src packages/*/test` for the two-package workspace layout). Its own `CLAUDE.md` is adapted, not copied: keeps TypeScript strict mode, Australian English/no em-dashes, small commits, and the three-part definition of done, but drops everything specific to the site agent itself (content-is-JSON-files, site-root-from-config, `node:sqlite` mandate, no-Liquid-tags rule) and references this repo's build plan/checklist by relative sibling path rather than duplicating them - confirmed directly with the user that the two repos stay fully separate (no parent monorepo), after weighing that option's cost (this session's working directory would stop being "the real one," and it becomes easier to accidentally import across the admin/agent boundary instead of going through the HTTP API) against its benefit (shared docs/`.claude` without cross-repo bookkeeping).

Design notes:

- **A permanent empirical smoke test before any route code, not README-trust**: `@fastify/session`'s docs don't fully specify whether `session.regenerate()` exists on the installed version or whether a custom store is callback- or promise-based. A dedicated test registering both plugins on a real Fastify instance settled both (regenerate exists and issues a new session id; the store contract is Node-style `(id, session, callback)`) before `session-store-adapter.ts`/`require-auth.ts` were written against an assumption - mirrors this repo's own precedent of never trusting a new dependency's interop without running it for real first (`@fastify/rate-limit`, Group A's `@fastify/static`).
- **A real TypeScript finding, not just a test result**: `@fastify/session`'s `Session` type only carries its own internal cookie options by default - `request.session.set('userId', ...)` doesn't typecheck without declaring custom session data via module augmentation (`packages/server/src/auth/session-types.ts`), found from a real `TS2345` error while writing the smoke test.
- **Two username-enumeration channels closed, not one**: B2's literal wording only names a message leak, but an unguarded implementation (skip password verification entirely when the username doesn't exist) leaks the same information through response *timing* instead - `scrypt` is deliberately slow, so skipping it for an unknown user is measurably faster. Fixed with a fixed `DUMMY_HASH`/`DUMMY_SALT` pair so `verifyPassword` always runs, win or lose.
- **`POST /api/auth/logout` is deliberately exempt from the auth guard, not an oversight**: guarding it would 401 exactly the already-expired/invalid session state logout exists to clean up. `GET /api/auth/me`, conversely, is *not* an exemption - it IS B1's mechanism (the frontend calls it to decide whether to redirect), so a 401 there is the guard working correctly, not a gap.
- **The auth-guard static-analysis test refines this repo's own `H2` fixed-character-window precedent, not a straight copy**: `routes/auth.ts` genuinely mixes an exempt route (login, logout) with a guarded one (me) in the same file, which would make a file-level "does `requireAuth` appear anywhere" check (this repo's own `B4` shape) pass trivially without ever catching a route that forgot the guard. Each route's window is bounded by the *next route registration* in the same file (or EOF), not a fixed character count - immune to the false-negative risk a fixed window has if a neighbouring route's guard declaration happens to fall within it. Verified two ways before being trusted: a synthetic mechanism check reproducing the exact exempt-then-guarded adjacency `routes/auth.ts` has, and a real scratch violation temporarily added to `routes/health.ts`, confirmed to fail the test, then reverted.
- **CSRF posture reasoned through explicitly, not left implicit**: cookie-based sessions reopen CSRF, which the site agent's bearer-token auth never had to consider. Verified empirically (not assumed) that Fastify's own default body parser rejects a form-encoded or multipart POST to a JSON-only route with 415 - combined with `SameSite=Lax` (blocks cookie attachment on cross-site mutations) and no `@fastify/cors` registered (blocks a genuine cross-origin JSON fetch via a failed preflight), this closes the one CSRF shape neither of those alone stops, without a dedicated CSRF-token library. Flagged forward, not fixed now: the first route accepting `multipart/form-data` for a real reason (asset uploads) reopens this exact hole and needs its own mitigation then.
- **A real CVE found and fixed via the audit trail, not the advisory's severity label alone**: `npm audit` flagged `react-router-dom`'s `react-router` dependency (7.12.0-8.2.0) for a CSRF advisory. Read the actual advisory rather than reacting to the label - it's scoped to unstable RSC server-action code paths this app doesn't use (plain `BrowserRouter`/`Routes`, no data router, no server actions), so it wasn't really exploitable here. Upgraded anyway to `react-router` v8.3.0 directly (v7 merged `react-router-dom` into the main package; only the import source changes, no API changes for plain declarative routing) rather than carry a flagged version while writing a "this is fine, actually" justification - a clean, compatible upgrade path existed (`react`/`react-dom` 19.2.8 already satisfy v8's `>=19.2.7` peer requirement), matching the same instinct that drove Group A's `@fastify/static` re-pin.
- **A real test-isolation bug, found while writing these tests**: `@testing-library/react`'s automatic `afterEach` cleanup only self-registers when it detects a *global* `afterEach`, and this repo deliberately doesn't set Vitest's `globals: true` (imports stay explicit everywhere). DOM from one test was silently leaking into the next within the same file (multiple "Log in" headings, multiple "Username" fields found by RTL's queries) until a `test/setup.ts` calling `cleanup()` was wired in via `vite.config.ts`'s `test.setupFiles`.
- **First-admin bootstrap** (open question, resolved directly with the user): auto-generates a username/password on first boot if the users store is empty (or uses `ADMIN_BOOTSTRAP_USERNAME`/`PASSWORD` if set), logged to stdout exactly once - mirrors this repo's own `create-site` "a real starter auth token is generated... printed once, never written to disk" precedent. Deliberately not called from `buildServer` (which must stay side-effect-free for tests); only `index.ts`'s real boot sequence runs it, verified live against a real fresh boot, not just asserted.

Design notes:

- **C5's own wording is technically wrong about this repo, found by reading the actual code before designing, not assumed**: it says "401 from capabilities," but `GET /v1/capabilities` here (`src/routes/capabilities.ts`) is completely exempt from auth - no `preHandler`/`requireScope` at all - and returns 200 regardless of whether a token is present, garbage, or missing. It can never produce a 401. The admin's `checkSiteStatus` therefore makes two sequential calls, not one: `GET /v1/capabilities` (unauthenticated - proves reachability and that this is really a cms-agent instance) then `GET /v1/content` (token-scoped, requires the `content` scope, a cheap side-effect-free GET) - only the second can actually prove a stored token is valid. Confirmed `GET /v1/content` with no query params returns `200 []` safely on a site with zero content, not an error, before relying on it as the probe.
- **This is the first place the admin actually calls out to a registered site's API**, and Group A's `A4` static-analysis guard (no hardcoded site URL, written before any site-calling code existed) and Group B's `B` guard (every route requires auth or sits on a reasoned exemption) both kept passing with **zero new allowlist entries** - exactly what both tests' own comments anticipated. `checkSiteStatus` builds every outbound URL via `new URL(path, site.url)`, never a literal `http(s)://` string, and every sites route carries its own inline `requireAuth`.
- **The raw site token is never sent to the browser, in either direction** - not on list, not on register, not on rotate. `SiteListEntry` (the response DTO) is built by an explicit mapping function rather than spreading the `Site` record, so a future refactor can't accidentally start leaking it. Token rotation is a pure overwrite with no pre-fill - the old value never reached the browser to begin with, so there was never anything to look up or echo back.
- **Registration is never gated on reachability** - a site with a bad URL/token is still added to the registry (metadata only, per C4's own framing); it just shows an unreachable/unauthorized status from then on, the same as any other entry. A deliberate, reasoned call rather than inventing a rejection flow nothing in the checklist asked for.
- **Live status on every list request, not a cached snapshot** - confirmed directly with the user against the alternative (stored status + an explicit "recheck" action): simpler data model, directly satisfies C5's "surfaced clearly in the registry list" without a stale-status risk, and acceptable at this project's expected scale (one admin instance, a handful of registered sites) since total list latency is bounded by the single slowest site's timeout, not the count of sites (`Promise.all`).
- **The registry UI replaces `HomePage.tsx`'s placeholder content in place at `/`, not a new `/sites` route** - flagged rather than silently decided: there's no nav bar anywhere yet, and the placeholder text ("Nothing registered yet.") already read as intentional foreshadowing. A real nav/layout shell is deferred until Group D adds a second real page that needs to link back to the registry.
- **Verified against a genuinely running second process, not just a scaffold fixture**: a real site was produced via the agent repo's own `create-site` CLI, packed with `npm pack` and installed from the tarball (not a `file:`-to-source-directory link, which would silently defeat the point), and booted as a real separate OS process on its own port. The admin's registry then registered it, rotated its token to a wrong value and back (watching the live status flip `ok` -> `unauthorized` -> `ok`), and deleted it while confirming the agent process kept running and answering `/v1/capabilities` unaffected - proving C4's "removal never touches the site" against a real process, not just by reading the handler's code.

Design notes:

- **D3's real scope, worked out before building anything**: Group E (the sidebar editor) doesn't exist yet, and its own E1 criterion ("opens a page for editing, reads its current content - draft if one exists, else live") makes clear the *editor* is what fetches/decides draft-vs-live, not Group D. So D3 is genuinely just correct navigation. But matching this project's own track record (every group ships something clickable, never a dead link) and CLAUDE.md's "no half-finished implementations," a minimal placeholder editor page was built at that route instead of leaving it to 404 until Group E - no fetch, no form, just path/site/known-status and an explicit "editing isn't built yet."
- **The backend content-list proxy does ONE call, not `checkSiteStatus`'s two.** `checkSiteStatus`'s capabilities-then-content sequence exists specifically because capabilities is auth-exempt and alone can't prove a token works - that matters for a health check. Listing content is calling the real resource actually wanted; that single call's own outcome (network failure, 401/403, non-2xx, malformed body, or success) already tells us everything.
- **Failures map to `502` with `{error, reason}` in the body, not a reused `401`.** `401` already means one specific thing everywhere else in this admin (the caller's *own* session is invalid, via `AuthError`/failed login) - reusing it for "the downstream site rejected our token" would be a real footgun the moment a global "on 401, log out" interceptor gets added later. `403`/`502` are unused anywhere in this server today (checked via grep, not assumed). `502` is semantically correct regardless of which of three ways the upstream failed, since this route genuinely is a gateway to another server - `reason`, not the HTTP status, is what the frontend branches on.
- **`fetch-site.ts` extracted as a narrow shared helper** (URL construction via `new URL(path, site.url)`, timeout wrapping, the network-failure try/catch only) once a second real caller needed the same shape - not a broad "site client" abstraction; each caller keeps its own interpretation of the response, since a 4-way health status and a 3-way content-fetch failure reason are different domain concepts. `checkSiteStatus`'s own existing test suite passed unchanged after the refactor, proving no behaviour change.
- **The content browser always makes its own live call, never gating on the registry's last-seen status** - Group C's own C5 principle ("live status on every list request, no cached snapshot") would quietly break one page over otherwise; a site can go unreachable/unauthorized between registration and a browse click.
- **A real test-isolation gap found by running the existing suite, not theorised**: `HomePage.test.tsx` rendered the component with no Router context, which broke the moment `HomePage` gained a `<Link>` for the new "Browse content" action. Fixed by wrapping every render call in a `MemoryRouter`, matching `App.test.tsx`'s already-established pattern.
- **No nav shell yet** - a trivial shared `BackToRegistryLink` component, not a layout route with persistent chrome. One link target, no multi-item navigation to speak of yet.

Design notes:

- **The read route does ONE fewer call than `checkSiteStatus` needs, and the write route reinvents nothing the site already got right.** `fetchSiteEditorContent` is two sequential calls (draft, falling back to live only on a literal 404), not `checkSiteStatus`'s capabilities-then-content dance - that dance exists specifically to prove token validity before trusting an auth-negative result, which doesn't apply here. A new shared `interpretSiteResponse` helper (not a richer per-operation union) handles the write route too: only "unreachable" and "401/403 remapped" need real interpretation - every other status (200, 404, 409, 428, 400) the site already produced correctly and is forwarded byte-for-byte.
- **401 is never reused for a downstream site failure.** In this codebase `401` means exactly one thing everywhere else - the caller's *own* admin session is invalid (`AuthError`/failed login). A downstream site's rejected token or conflict is `502`/`409`/`428` with a `{error, reason}` body instead, closing off a real footgun (a future global "on 401, log out" interceptor would otherwise misfire on a downstream failure).
- **`fetch-site.ts` was extended (method/headers/body), not bypassed**, so the write path still builds its URL through the one function that keeps `A4`'s hardcoded-URL guard passing. `site-status.ts`/`site-content.ts`'s full test suites (24 tests) passed unchanged after the extension, proving no behaviour change.
- **ETags are fully opaque pass-through strings, verified empirically, not trusted from the dependency list**: a quoted `ETag` round-trips through `fetch` + `interpretSiteResponse` with its quotes intact, settling whether undici or Fastify's own header handling could mangle it before any route was built against that assumption.
- **The autosave state machine is single-flight with a queued follow-up, not cancel-and-restart or overlapping saves** - refs (not just React state) back etag/content/in-flight/pending-save so the debounce timer and chained saves always read synchronously-current values. A `409` stops the loop entirely (not just the current attempt) until an explicit reload; malformed JSON is caught client-side so the backend never has to handle it.
- **`loadComparison` (E5) reuses the exact same draft-then-live read as the initial load, not a live-only fetch** - the far more common real conflict source is another tab's own *draft* autosave (E6's own scenario), and a live-only comparison would show the wrong thing for exactly that case.
- **No diff library**, consistent with this checklist's own still-open Group H question - "view what changed" is the server's latest text and the user's own unsaved text shown side by side, verified live to render both correctly.
- **A real fake-timers/RTL `waitFor` deadlock, found while testing, not theorised**: mixing Vitest's fake timers with `waitFor` hangs, since `waitFor` polls via the same timer mechanism the fake clock freezes. Fixed with an optional `debounceMs` parameter on the hook (defaults to 1000ms) and real timers with a tiny value in the hook's own tests; `PageEditorPage`'s own tests instead use an explicit longer `waitFor` timeout rather than threading test-only plumbing into the component.
- **A real shell-quoting bug, found in the verification script itself, not the product**: a `bash -c` string with an interpolated `ETag` value (which itself contains literal quote characters) silently produced a malformed `If-Match` header, making the wrong side of a simulated two-tab race fail. Fixed by calling `curl` with an argument array instead of a shell string, avoiding the quoting collision entirely - worth recording since it's exactly the kind of mistake that would misreport a real product bug as passing.

Design notes:

- **The agent gained one small, additive change: a `url` field on `GET /v1/content`.** The editor only ever held a content *file path* (`pages/about.json`), never the public URL the preview route needs (`/about`) - the conversion already existed agent-side (`pagePathToUrl`/`postPathToUrl`, previously only used internally by `move.ts` for redirect generation on rename) but had never been exposed via any route. Computed server-side by reusing those exact functions after stripping the `pages/`/`posts/` prefix, so the URL scheme stays single-sourced where it's actually implemented, rather than re-derived independently on the admin side. Menu entries have no public URL (`url: null`) - the preview component shows a plain fallback message instead of pointing an iframe at nothing.
- **`GET /v1/preview/*` already does its own draft-over-live overlay and its own 404** - unlike Group E's editor-content route, the admin's `site-preview.ts` needs only one call, not a draft-then-live sequence, and forwards whatever comes back with no interpretation of its own. This is what makes F3 true rather than merely claimed.
- **One narrow exception to "forwarded byte-for-byte", found via real dogfooding, not anticipated up front**: the rendered HTML's root-relative asset references (`href="/assets/style.css"`) are meant to resolve against the *site's* own origin, but once embedded in the admin's iframe the document was actually loaded from the admin's own proxy URL, so the browser resolved them against the admin's origin instead - silently hitting the admin's own unrelated `/assets/*` route (its SPA fallback) rather than 404ing loudly, so the failure looked like "no styling" rather than an obvious broken link. `site-preview.ts` now injects a single `<base href="{site.url}/">` tag into the `<head>` of any `text/html` response (a no-op if there's no `<head>` to attach to; untouched for the 404 JSON case). This only changes how the browser resolves resource URLs - it does not alter the page's actual rendered content or draft state, so F3's "not a client-side approximation" guarantee still holds for what the criterion is actually about.
- **The proxy forwards the real `Content-Type`, not a fixed one.** `interpretSiteResponse` (Group E's shared helper) doesn't carry content-type today, since its two existing callers (E1 read, E2 write) both fix their own and never needed the site's real one. Rather than widen a helper three routes depend on for this one new caller, `site-preview.ts` reads `content-type` directly off the raw `Response` at the one call site that needs it - headers access doesn't consume the body stream, so this is safe alongside `interpretSiteResponse`'s own `arrayBuffer()` read of the same result. Lower blast radius than touching shared surface area three routes already depend on.
- **F2 is a plain React-level src reassignment, not `window.postMessage`.** The previewed document is static server-rendered HTML, not a React app with its own JS that needs to talk back to the parent - there is no cross-frame data to relay, only a "reload yourself" signal, which changing the iframe's `src` (with a cache-busting token) already accomplishes natively without touching the admin SPA's own router or state. The refresh token only bumps on the specific `'saving' -> 'ready'` transition, tracked via a `ref` local to the new `PreviewFrame` component - `useAutosaveDraft` itself stays untouched, since it's deliberately UI-agnostic per Group E's own I6 note and touching it would re-open all of Group E's test surface for no functional gain. A `'loading' -> 'ready'` transition (the "Reload latest version" conflict-recovery path) needs no equivalent handling: `PageEditorPage` unconditionally renders a loading placeholder in place of the whole editor (including `PreviewFrame`) whenever status is `'loading'`, so the preview frame unmounts and remounts fresh as a genuinely new iframe element on recovery, rather than needing a second explicit refresh trigger.
- **`url` threads through as a second query parameter (`&url=...`), not router state**, for the same reason `path` already does: a bookmarked or directly-reloaded editor URL must keep working, and route state doesn't survive that. `path` stays the sole key for the existing content-read/draft-save routes - `url` is purely additive, consumed only by `PreviewFrame`.
- **Verified live end-to-end** against a real second `create-site`-scaffolded agent instance (rebuilt and repacked after the `url`-field change, reinstalled from a fresh `file:` tarball): registered the site, opened the homepage (a real draft differing from live) and confirmed the iframe showed draft content; edited the textarea and watched the iframe refresh automatically after the real autosave landed, with the admin app's own URL never changing; opened a page with no draft and confirmed the real live-fallback content rendered; opened a menu entry and confirmed the "No live preview available for this content type" fallback, no broken iframe.

Design notes:

- **The commit author is never typed by the caller.** Publish/unpublish both need a real git commit author (`{name, email}`), which the admin's `AdminUser` model had no room for. Decided with the project owner: stored on the admin account itself, set once at bootstrap (`ADMIN_BOOTSTRAP_NAME`/`ADMIN_BOOTSTRAP_EMAIL` env vars, defaulting to the username and a synthetic `id@admin.local` address), not typed fresh per publish and not derived per-request. `require-auth.ts`'s `currentUser` widened to carry it through to route handlers, which build the `CommitAuthor` server-side - the browser only ever supplies a path and a commit message. A quiet backfill runs at every boot for any pre-existing account (Groups A-F) missing these fields, so upgrading an existing deployment never leaves an invalid record on disk.
- **Publish is single-page from the browser's point of view, even though the agent's own route is a batch API.** The browser sends `{path, message}`; the admin route wraps it into the agent's real `{paths: [path], message, author}` shape server-side. This keeps `site-publish.ts` a faithful 1:1 mirror of the real API (reusable if multi-select publish is ever added later) while "this UI is single-page only" stays a route-layer decision, the same separation `parseContentFilters`/`fetchSiteContent` already keep in Group D.
- **Three separate backend modules** (`site-publish.ts`, `site-draft-discard.ts`, `site-unpublish.ts`), matching this codebase's existing one-file-per-site-operation granularity (`site-draft-save.ts`, `site-preview.ts`) rather than combining them.
- **No new frontend error class or path-encoding helper.** `site-editor.ts`'s existing `SiteEditorError`/`SiteEditorErrorReason` already covered every reason these three calls need; its private `encodePathSegments`/`reasonFromResponse` helpers were simply exported (visibility widening only) and reused directly from the new `site-publishing.ts`.
- **`useAutosaveDraft` was not modified.** Publish/discard/unpublish are a separate concern layered beside it in `PageEditorPage.tsx` (local `actionBusy`/`actionError` state), calling the hook's own `reloadLatest()` only after a successful action - this is what makes G5 true by construction, not bolted on afterwards.
- **Publish is disabled while the editor's own status is `dirty` or `saving`.** `POST /v1/publish` publishes whatever is already saved as a draft on disk, not the browser's current textarea content - publishing mid-edit, before the debounce fires, would silently ship stale content. Only enabled once a save has actually landed (`status === 'ready'`).
- **Discard reuses `HomePage.tsx`'s existing `window.confirm` precedent exactly** (Group C's site-removal confirmation) rather than inventing a new confirmation pattern. Publish and unpublish each use `window.prompt` for the commit message; no second confirm on unpublish beyond that, since it's reversible by republishing and the checklist doesn't call for one.
- **`ContentBrowserPage.tsx` needed no changes at all** - it already performs a fresh, uncached fetch on every mount (Group C/D's "always live" principle), so navigating back after a publish/discard/unpublish already shows current state with zero new code.
