# Phase 2 acceptance checklist - site agent API and first packaged release

Rules for using this file (same as Phase 1):

- An item is done only when its proving test exists, passes, and is named in the "Proof" column. "It works when I run it" is not proof.
- Work top to bottom within a group; groups are ordered by dependency.
- When all items in a group are proven, commit with message `phase2: <group> complete`.
- Do not edit the criteria to match the implementation. If a criterion is wrong, raise it with the lead first.
- Each group gets its own working session: research any new dependency/API empirically before designing (as Phase 1 did for LiquidJS and `node:sqlite`), a plan-mode design review for anything with a real architectural decision, then implement in small commits.

## Open questions carried in from scoping (resolve at the named session, not before)

1. ~~Is `GET /v1/capabilities` exempt from auth, or does it need any valid token?~~ **Resolved in Group B: exempt, no token required.** It's the one route a client needs before it necessarily has a working token configured, and it leaks a version/feature banner, not content — comparable in kind to an HTTP `Server` header. Noted for later: once Group H's rate limiting lands, this is the natural first thing to rate-limit, being reachable with zero credentials.
2. Does `DELETE /v1/content/:path` support deleting a page with children (subtree delete), or reject it outright? The build plan's phrasing is singular-page; it doesn't say. (Group F)
3. Draft-checkpoint commit identity (Group H) — the same shape of question `src/boot.ts` already declined to answer for boot-time migrations (`src/services/migration-runner.ts`): what identity should an unattended, no-human-editor git commit use? Reintroducing a host-git-config fallback would walk back the Phase 1 H3 sign-off that commits never depend on host config. Decide whether boot-migration and checkpoint share one system identity or get separate ones.
4. Media (Group I): route-stub-only is the recommended default, not a locked decision — confirm or revise at that session.
5. ~~CORS: implied by Phase 3's admin-iframe/postMessage description but never mentioned anywhere in the build plan.~~ **Resolved in Group B: not implemented, deferred to Phase 3.** Firmer reason than "no admin app yet": this API's auth is a bearer token in an `Authorization` header, never a cookie — the primary reason CORS matters for security (protecting cookie-authenticated endpoints from cross-site request forgery via ambient credentials) doesn't apply here. A cross-origin page cannot attach an `Authorization` header without triggering a CORS preflight the server would have to opt into, so there's no ambient-credential attack surface being left open by omission — this is a pure browser-JS-enablement question, not a security gap, and belongs to Phase 3 once the admin's registered-sites/origins model exists to define an allowlist against.

Design notes worth recording, not just the proof pointers above:

- **C7 added mid-session, not originally scoped**: raised directly by the user while manually exercising the dev server against the fixture site. `index.json` needed no new code at all — `/` already resolved to `content/pages/index.json` since Phase 1 (`urlToPagePath`/`pagePathToUrl`'s own round-trip test proves it); the fixture simply didn't have one. The 404 page is genuinely new: `sendNotFound` in `src/routes/public.ts` attempts `renderPage(..., 'pages/404.json', 'public')` exactly like any other page — no special-casing added to `render-page.ts` itself, no bypass of the existing `published` filter, so an unpublished `404.json` correctly still falls back rather than leaking a draft error page. Any failure at all while attempting the themed 404 (missing, unpublished, or its own theme broken) falls back to the plain JSON error rather than ever compounding into a 500 - confirmed by a dedicated regression test disabling `published` on a fixture 404.json. Scoped to the public route only, not `/v1/preview/*` (explicit decision - an editor previewing a broken URL wants a diagnostic, not a styled error page).

- **A real double-prefix bug, caught by these tests, not by inspection**: Fastify passes the *entire* options object a plugin was registered with — including `prefix` — through as that plugin's own second argument. The first draft of `src/routes/index.ts` passed that `opts` object straight through to `fastify.register(previewRoutes, opts)`, which silently carried `prefix: '/v1'` along with it and double-applied it (`previewRoutes` ended up registered at `/v1/v1/preview/*`, confirmed via `app.printRoutes()` and direct `app.inject()` probing before the fix). Fixed by re-packing only the site-data fields (`config`, `themeTemplates`, `tokens`) for the nested `register()` call, never forwarding `opts` itself. Left as a commented warning in `src/routes/index.ts` for the next route group that needs the same plumbing.
- **A second gotcha, verified empirically before it could bite**: the public route's `GET '/*'` catch-all, registered without a `/v1` prefix alongside `v1Routes`, would otherwise swallow *unmatched* `/v1/*` requests (e.g. a typo'd or future-removed API path) and serve them as page lookups instead of Fastify's real 404 — breaking Group A's A4. Fixed with an explicit guard in `src/routes/public.ts` (`if (request.url.startsWith('/v1/') || request.url === '/v1') return reply.callNotFound();`), proven by `test/routes/public.test.ts :: an unmatched /v1/* path is never swallowed by the public catch-all as a page lookup`.
- **`resolveUrl`/`renderPage` seam**: `resolveUrl`'s `relativePath` is relative to `config.pagesRoot`, but `renderPage`'s is relative to `config.contentRoot`/`draftsRoot` directly — the two already-correct, already-tested Phase 1 modules use two different conventions for the same string. Both `public.ts` and `preview.ts` join `'pages'` onto the path before calling `renderPage`, commented at the point of use so it doesn't read as an arbitrary literal.

Design notes:

- **A schema decision raised to the user rather than invented**: the build plan names a `type` filter for `GET /v1/content` with no backing field anywhere in the page schema. Raised as an explicit question; the user chose to add a real `type` field now via a proper migration (`src/schemas/page.schema.json`, `CURRENT_SCHEMA_VERSION` 2 → 3, `migrateV2ToV3` defaulting existing content to `type: "page"`) rather than omitting the filter or reinterpreting it. The blast radius (every caller of `validatePage`) was scoped by reading each one before writing any code.
- **A design-review claim that turned out to be wrong, caught by running the suite, not by inspection**: the plan review asserted `test/services/migration-runner.test.ts` was unaffected by the schema change because its tests use fully local, decoupled `MigrationMap`s. That's true for the migration *map*, but `runMigrationsJob` unconditionally validates migrated output against the real `page.schema.json` regardless of which map drives it — so its `page()` helper still needed the new required field. Recorded here as a reminder that "doesn't import the real chain" and "unaffected by a schema change" are not the same claim.
- **ETag algorithm**: a plain `sha256` content hash (`src/services/etag.ts`), not a git blob hash — `git.ts` only shells out for actual commits, never a per-request read, and no later group needs the ETag to coincide with a real git blob hash. One shared `computeEtag` function for both these reads and Group E's future `If-Match` comparison, never inlined separately.
- **`:path` convention**: `:path` for D1/D2 is relative to `config.contentRoot`/`config.draftsRoot` directly (e.g. `pages/about.json`), matching `renderPage`'s own convention — deliberately avoiding a second seam-translation point like the one Group C's `public.ts`/`preview.ts` needed against `resolveUrl`'s pagesRoot-relative convention.
- **D3's scope**: the listing is the union of `contentRoot` and `draftsRoot` paths, not live content alone — Group D's own heading is "content **and draft** reads," and there is no separate "list drafts" endpoint anywhere in the build plan, so this is the only place a draft-only page is discoverable at all.

| E6 | Two requests racing to `PUT` the same path with the same now-stale `If-Match` value: exactly one succeeds, the other gets 409 — not two successes (delay-injection test, mirroring Phase 1's C1) | `test/services/drafts.test.ts :: E6: two concurrent saves racing with the same now-stale If-Match value ...` — **the real regression proof, no artificial delay** (see design note below); `test/routes/drafts.test.ts :: E6 (HTTP wiring sanity, not the regression proof): ...` confirms the real endpoint resolves the same way end-to-end, but is explicitly not relied on as the proof itself |

Design notes:

- **A design-review conclusion overturned by empirical testing, not just reasoned about**: the review argued no artificial delay is needed for E6, reasoning that `write-queue.ts`'s true one-at-a-time job execution makes the outcome timing-independent for a *correct* implementation (verified: 2000 trials, 0 failures). But the *naive* design (`If-Match` checked before `enqueue`, only the write queued) also produced the bug 2000/2000 times when called directly — yet did **not** reproduce in a single `app.inject()`-based HTTP trial, because Fastify's own request-dispatch overhead was enough noise to accidentally close the naive design's race window. Conclusion: E6's real regression proof has to call `saveDraft` directly (service layer), mirroring exactly how Phase 1's own C1 tested the raw `enqueue()` primitive rather than through HTTP — an HTTP-only test would be an unreliable proof, able to pass against genuinely broken code by scheduling luck.
- **Verified, not assumed, that the E6 test actually catches a regression**: before trusting it, the correct design was temporarily reverted to the naive (check-before-`enqueue`) shape and the service-layer E6 test was confirmed to fail against it (both requests succeeded, `2 !== 1`) — a positive control, matching this codebase's own `test/static/static-analysis.test.ts` B4-mechanism-check precedent — then reverted back.
- **The `If-Match` check lives inside `saveDraftJob`, never at the route layer before `enqueue`** — the TOCTOU gap a prior scoping session's memory note already flagged for this exact group. E1 (header presence) is the one exception, correctly handled at the route layer instead, since it's a static per-request property with no shared mutable state to race against.
- **The "brand new page, no live, no draft" case is deliberately unchecked against a specific `If-Match` value** — not one of E1-E6, and not a race loophole in practice: the first write to a wholly new path skips the comparison, but any *second* write to that same path lands after a real draft now exists, so it's checked for real against an arbitrary placeholder's near-zero odds of matching.

Design notes:

- **The checklist's own open question (F3 subtree delete) was resolved before implementation, not invented**: raised directly, the user chose reject-outright (409) over cascade delete.
- **A real bug caught by design review before any code was written**: the first draft of F3's subtree-rejection check used bare directory existence, which would have made a page with a leftover *empty* sibling directory permanently undeletable (no rmdir/cleanup endpoint exists anywhere in this API to ever clear it). Fixed to check for a real child page via `listFilesRecursively`, proven by its own regression test (`test/services/delete-content.test.ts :: a leftover empty sibling directory does not block deletion`).
- **A new `redirect-cycle` reason for `DeleteContentError`, not swallowed into the generic 500**: unlike `publish.ts`/`move.ts`'s own automatic redirect bookkeeping, F3's `redirectTo` is client-supplied, so a client can trivially trigger a real cycle — that's a 400-shaped input error, not an unlikely internal failure.
- **`isValidCommitAuthor` (`src/services/git.ts`)**: the first place a caller-supplied identity reaches `git commit --author` anywhere in this codebase (`saveDraft`/`discardDraft` never take an author at all) — rejects control characters (`\n`/`\r`) in addition to requiring non-empty `name`/`email`, since `execFileSync` alone only rules out shell injection, not a malformed multi-line author string in git history.
- **A gap caught by the tests, not by inspection**: the first draft of `routes/publish.ts` only caught `PublishError`, leaving `PathSafetyError` (no `.statusCode`) to fall through to a sanitised 500 instead of the 404 every other `:path`-touching route already gives. Fixed to match that established pattern before this checkpoint's tests were trusted.

F5/F6 (batch operations) design notes:

- **A real ambiguity in the build plan's own wording, resolved before design started**: batch's "deletes" operation could mean draft-discards, live content deletes, or both. Asked directly — the user chose both, so `BatchOperation` has distinct `draft-discard` and `content-delete` variants.
- **`publishDrafts`/`movePage`/`deleteContent` split into `prepareX`/`xJob` pairs**, a new shared `PreparedOperation` shape (`{ paths, undo }`, `src/services/prepared-operation.ts`): `prepareX` validates and writes, stopping short of the commit; `xJob` calls `prepareX` then commits. Every existing exported function's signature and behaviour is unchanged — proven by the full existing test suite passing unmodified. `drafts.ts` grew matching `prepareSaveDraft`/`prepareDiscardDraft` exports (rejected in design review: doing this snapshotting ad hoc inside `batch.ts` instead, reaching into another module's on-disk layout).
- **A real bug caught by design review, verified empirically before coding**: a batch of pure `draft-write`/`draft-discard` operations produces zero git-tracked paths (drafts are never git-tracked), and `git commit` with nothing staged exits non-zero ("nothing to commit") — confirmed with a real scratch test, not assumed. `batchJob` explicitly skips the commit when the accumulated path list is empty, rather than surfacing a spurious `commit-failed`.
- **No whole-batch duplicate-path pre-check** — rejected in review. Undo across batch *operations* runs in reverse chronological order (unlike `publishDrafts`'s own internal duplicate-path guard, which protects a different, forward-order multi-snapshot restore), so a `move A→B` then `content-delete B` in the same batch correctly unwinds with no special-casing, and genuine conflicts are already caught fresh by each sub-service's own real-time validation as operations are processed sequentially. A batch-wide guard would have broken legitimate write-then-publish or move-then-delete chains.
- **A test gap in `move.ts` closed as part of this work, not a new requirement**: `test/services/move.test.ts` had no commit-failure/rollback test at all before this session (only `source-not-found`/`destination-exists`). Added one mirroring `delete-content.test.ts`'s `index.lock` technique, so `move.ts`'s prepare/commit split had something real to verify against.
- **A second real bug, caught only once the route's path-traversal test was written**: `batchJob`'s rollback fallback originally labelled *any* non-domain error reaching it as `commit-failed`, including a `PathSafetyError` thrown deep inside a `prepareX` call (e.g. a `../` path in a `content-delete` operation) — turning a safe 404 into a bare 500. Fixed so only a failure from the post-loop `commitPaths` call (no `stage` set) gets the `commit-failed` label; an unrecognised error surfacing during the operations/publish loop is rethrown as-is so the route's own `PathSafetyError` check still sees it.

Design notes:

- **The checkpoint message convention was already settled by the build plan** (`chore: draft checkpoint`, from Group H's not-yet-built background job) - Group G only had to flag it, not invent it. Flags by **exact** message match, not a prefix, so the existing `migration-runner.ts` automated commit (`chore: migrate content to schema version N`) - a different, meaningful category - is never misclassified as checkpoint noise. The checkpoint commit's *author identity* is a separate, still-open question (this doc's own carried-forward open question 3) that Group G deliberately does not attempt to resolve - it belongs to Group H's own session.
- **A Plan-agent design review caught several real bugs before any code was written**, all folded into the implementation rather than left as risks: (1) git's `--format=`/`tformat:` appends its own newline terminator after every record, which lands as a leading `\n` on the *next* record - naive splitting on a custom record separator would silently misparse every commit but the first; verified empirically against a real multi-commit repo (including one with an embedded multi-line message) before trusting the fix. (2) `sanitisePath`'s absolute return value is correct for a `--` pathspec argument (`git log -- <path>`) but *wrong* for the `<rev>:<path>` colon syntax `git show`/`git cat-file` use, which resolves `<path>` relative to cwd - the repo-relative string has to be re-derived via `relative()` from sanitisePath's own already-validated result. (3) `git cat-file -t <ref>:<path>` succeeds for a directory (tree) too, not just a file (blob) - without an explicit type check, requesting a directory path would make `git show` print a plain-text directory listing formatted as if it were file content, with a wrong Content-Type. (4) A brand-new site's repo can exist with zero commits until the first publish/checkpoint/manual commit ever happens - plain `git log`/`git rev-parse` on a HEAD-less repo exits non-zero, which without a guard becomes an uncaught 500 for what should just be an empty history.
- **`git/revert` hit its own shape of the batch.ts empty-commit lesson**, triggered by content-identity rather than an empty path list: `git checkout <ref> -- <path>` always stages *something* even when the reverted content is byte-identical to what's already live (e.g. reverting to `HEAD`, or a double-submitted revert), which would otherwise make `git commit` fail with "nothing to commit" for a request that didn't do anything wrong. Guarded via `git diff --cached --quiet` scoped to just the reverted paths (not the whole repo, so an unrelated pre-existing dirty index - exactly what `/git/commit`'s escape hatch is for - is never mistaken for a no-op revert).
- **`git/show` and `git/revert` deliberately do *not* collapse their two failure reasons into one status code**, unlike `public.ts`'s deliberate traversal-vs-miss collapse. That collapse is justified specifically because the public route is unauthenticated, where leaking which case occurred would aid enumeration; these two routes already sit behind `requireScope`, so there's no equivalent risk, and collapsing here would only make an admin's diff/history UI worse for no security benefit. `invalid-ref` → 400, `not-found-at-ref`/`path-not-found-at-ref` → 404.
- **`ref` validation is an allowlist regex, not a denylist** (`^[A-Za-z0-9._/-]+$`, no leading `-`, no `..`) - the same reject-on-ambiguity posture `sanitisePath` already uses for paths, closing off flag-injection and reflog/traversal-shaped refs in one line rather than enumerating each dangerous case as it's discovered.
- **`git/commit`'s escape hatch (`git add -A`) is deliberately unscoped** - a path-scoped variant would defeat the entire point of "out-of-band changes the API doesn't otherwise know about." It needs no `PreparedOperation`/undo-stack, unlike every other write service in this codebase: publish/move/delete/revert all *write new content themselves* on request, so a write can fail independently of the git step and needs an undo; here the "write" already exists in the working tree before the endpoint is ever called, so the only failure modes are `git add`/`git commit` themselves, which a bare `git reset` already unwinds.
- **`move.ts` is not extended for revert composability** - `POST /v1/git/revert` is not wired into `batch.ts` as a new `BatchOperation` variant, matching the same scope discipline Group L applied to not extending `move.ts` to posts. Nothing has asked for it.
- **`assets.ts`'s inline `MIME_TYPES` table was extracted to `src/services/mime-types.ts`** so `git/show`'s `Content-Type` inference could reuse it without a route-to-route import - zero behaviour change to `assets.ts`, confirmed by its existing test suite passing unmodified.

- **Six design decisions resolved directly with the user before and during design, not invented**: posts get a fixed `/blog/<slug>` URL prefix (not arbitrary paths like pages); posts require `author`/`publishDate`/`tags`; menus go through the same draft-then-publish git workflow as pages (not direct-write config); menus are a flat list of `{label, url}` (no nested/dropdown items for now); `/blog/` is a permanently reserved namespace (checked first, never falls through to page resolution even on a miss); `publishDate` is validated as a non-empty string only (no regex/format, no new dependency).
- **A Plan-agent design review confirmed the codebase's existing machinery is mostly already generic**, and scoped the work to targeted, justified extensions rather than a speculative "content type registry": `content-read.ts`'s `listContent` and every route in `content.ts`/`drafts.ts`/`publish.ts`/`batch.ts` already operate on arbitrary relative paths under `contentRoot`/`draftsRoot` with zero `pages/`-specific hardcoding - posts and menus became readable/writable/deletable/movable/batchable through the existing routes the moment validation became type-aware (L2/L3).
- **`post.schema.json`/`menu.schema.json` are genuinely separate schemas, not `page.schema.json` plus optional fields** - structurally forced, not a style choice: `page.schema.json`'s `additionalProperties: false` means a post's `author`/`publishDate`/`tags` would fail that schema outright regardless of whether they were declared required or optional there.
- **`validation.ts`'s shared envelope+sections-recursion logic was extracted into a private helper reused by both `validatePage` and `validatePost`** - genuinely load-bearing for two real content types now, not a speculative abstraction. `validateContent` dispatches on the relative path's prefix, not an in-file `type` field, since a menu has no `type` field at all and the right schema must be known before the content is even parsed.
- **`migration-runner.ts` needed a real, non-trivial change**: its file-walk loop discarded the relative path after joining it into an absolute one, so it couldn't dispatch `validateContent` correctly. Now carries `{path, relativePath}` through the loop.
- **A real correctness gap found while writing tests, not just theorised**: unlike `pagesRoot` (always expected to exist on a real site), `postsRoot`/`menusRoot` are optional - a site that has never used posts/menus has no `content/posts/`/`content/menus/` directory at all. `sanitisePath` calls `realpathSync` directly on its root argument, which throws a raw, uncaught `ENOENT` if that root is missing. `resolveBlogUrl` now checks `existsSync(config.postsRoot)` before ever calling `sanitisePath`, so an ordinary "no posts yet" site resolves any `/blog/` URL safely to not-found instead of crashing. `menus.ts`'s `loadMenus` has no equivalent gap - `listFilesRecursively` (unlike `sanitisePath`) already returns `[]` gracefully for a missing directory.
- **`move.ts` is deliberately not extended to posts in this pass** - scope discipline, not an oversight: nothing in the confirmed requirements asks for renaming a post's slug, and parametrizing `move.ts`'s subtree-walk behind a flag that's permanently unused by posts (flat, fixed-slug) is exactly the kind of generalize-for-a-hypothetical this codebase's own anti-overengineering ethos warns against. A `/blog/...` URL passed to `POST /v1/content/move` today harmlessly 404s rather than corrupting anything - verified as a test (L3's proof column), not just asserted.
- **`delete-content.ts`/`publish.ts`'s `PAGES_PREFIX`-gated redirect bookkeeping widened via a tiny duplicated `urlForDeletedEntry`/`urlForPublishedEntry` helper in each file, not a shared "collection" abstraction** - matches this codebase's existing precedent (e.g. `prepareSaveDraft`/`prepareDiscardDraft` mirror rather than share a base with `publish.ts`/`move.ts`). The `has-children` subtree-protection check in `delete-content.ts` is untouched (`PAGES_PREFIX`-only) - posts never have nested children by construction.
- **Menus are scoped to the layout only, not sections/blocks** - matches the literal confirmed requirement ("so a layout can render nav from it"). Threading `menus` into `renderSections`/`renderInstance` too is a cheap, natural follow-up if a theme author later wants a nav-rendering section, not worth pre-building now.

## Group M: redirects as first-class, marketing-manager-authored content

Not in the original build plan anywhere - added mid-phase at the user's request after a real, recurring need was described directly: marketing managers routinely need to point a URL (e.g. a campaign landing page) at a new destination independent of any page move or delete. This resolves the build plan's long-open question of whether `redirects.json` should be schema-validated content with its own editor surface, or stay machine-written plumbing - it's now the former, with the explicit decision that it needs no draft/publish two-step (every write commits immediately, since there's no separate draft state to hold it in).

| # | Criterion | Proof |
|---|---|---|
| M1 | `redirects.json` is schema-validated content (`{schemaVersion, entries: [{from, to, note?}]}`, `src/schemas/redirects.schema.json`); the old flat-map shape is transparently upgraded in memory on read; a malformed new-shape file returns empty on the graceful read path but is refused loudly on the stricter write path | `test/services/redirects.test.ts :: loadRedirects upgrades the old flat-map shape ...`, `:: loadRedirects gracefully returns empty entries for a malformed new-shape file ...`, `:: loadRedirectsStrict throws on the same malformed new-shape file ...` |
| M2 | Chain-collapse (moving/updating a redirect that other entries point through) surfaces which pre-existing entries were retargeted, rather than silently rewriting a human-authored, note-bearing entry with no signal | `test/services/redirects.test.ts :: addRedirect returns the retargeted entries ...`, `test/services/manage-redirects.test.ts :: createRedirect surfaces retargeted entries ...` |
| M3 | A marketing manager can create, update, and delete individual redirect entries directly (`GET/POST/PUT/DELETE /v1/redirects`), independent of any page operation, each write committing immediately with no draft step | `test/services/manage-redirects.test.ts`, `test/routes/redirects.test.ts` |
| M4 | Redirect targets are restricted to internal paths only (closes an open-redirect risk), enforced identically by the new endpoints and retroactively by the pre-existing `DELETE /v1/content/:path`'s client-supplied `redirectTo`, which previously had no format validation at all | `test/services/manage-redirects.test.ts :: createRedirect rejects an external target`, `test/services/delete-content.test.ts :: deleting a page with an external redirectTo is rejected ...`, `test/routes/content.test.ts :: F3: DELETE /v1/content/:path with an external redirectTo returns 400 ...` |
| M5 | Creating a redirect at a URL that already has live content (a page or post) is rejected with a clear error rather than silently accepted and never firing | `test/services/manage-redirects.test.ts :: createRedirect rejects with live-content-exists ...`, `test/routes/redirects.test.ts :: POST /v1/redirects maps a from that already has live content to 409` |
| M6 | The three existing automatic redirect writers (publish/delete/move) are unchanged in behaviour, only adapted for the new on-disk shape; `create-site`'s scaffold template ships the new shape | Existing `test/services/publish.test.ts`/`test/services/move.test.ts`/`test/services/delete-content.test.ts` E5 suites, all green against the new shape; `src/create-site/template/redirects.json` |

Design notes:

- **Location stays at the site root**, not moved into `content/`/`drafts/` - raised as a real question ("should redirects.json live under content/ since it's tied to page structure") but resolved once "no draft step" was decided: the entire motivation for moving it was wanting a draft/live duality, which a file with no draft state doesn't need. Moving it would also have reopened the project's #1 security concern for no benefit: `redirects.json` deliberately sits outside the path-sanitised `contentRoot`/`draftsRoot` boundary today (`redirects.ts`'s own comment: "never a request-supplied `:path`"), and the new manual CRUD routes take `from`/`to` from the JSON body specifically to keep it that way, never as a URL path segment.
- **A Plan-agent design review caught three real gaps before code was written**: (1) the old-shape/malformed-new-shape distinction needed to be a genuine shape check, not "did JSON.parse succeed," or a corrupt new-shape file would be silently treated as an empty old-shape map and a subsequent write would destroy real data; (2) the open-redirect question wasn't actually a new decision - `delete-content.ts`'s `redirectTo` was already unvalidated in shipped code, so whatever rule got chosen had to apply retroactively there too, not just to the new endpoints; (3) chain-collapse silently rewriting a note-bearing entry's target needed to be surfaced, not just left as an implicit side effect.
- **`loadRedirects` (graceful) and `loadRedirectsStrict` (throws) are deliberately two different functions**, not one function with a flag: public request handling (`resolve-url.ts`/`resolve-blog-url.ts`) must never crash on a corrupt `redirects.json` - matching `theme-schemas.ts`'s established graceful-on-any-failure precedent - while a write path (`manage-redirects.ts`) must never silently treat a corrupt file as empty and overwrite it, since that's a data-loss bug waiting to happen.
- **The three existing automatic writers (`publish.ts`/`delete-content.ts`/`move.ts`) are not refactored to route through the new `manage-redirects.ts` functions** - each keeps its own direct call into `redirects.ts`'s pure helpers, mechanically adapted for the new shape, because routing them through a separately-enqueued redirect commit would fragment their existing one-commit-per-operation atomicity (e.g. `move.ts` bundles every affected page plus `redirects.json` into a single commit). Because `write-queue.ts` is one shared global FIFO for every enqueued job in the process, the new manual operations still serialise correctly against the existing writers with no extra coordination needed.
- **Not extended to `batch.ts` in this pass** - a client cannot yet bundle a manual redirect create/update/delete atomically with a move/delete/publish in one commit. Nothing in the confirmed requirements asked for it; stated here as a deliberate scope line, not a silent gap.
- **`note` is freeform text with no `source`/`createdAt` provenance fields** - git history (author and commit message, already required on every write) already carries who/when; duplicating it inside the JSON would be redundant with the project's own "git is the audit trail" philosophy.

## Group N: scaffold restructuring - content/theme/vhost, menus become direct-write

Not in the original build plan anywhere - added mid-phase at the user's explicit request for a tidier top-level scaffold layout (exactly `content/`, `theme/`, `vhost/`), plus a follow-on request that menus behave like `redirects.json` (no draft/publish step). `vhost` is a deliberate, correct name, not just a sort-order trick: in real hosting terms (Apache/nginx/CyberPanel) a vhost is the per-site serving configuration, one per site - this folder holding package.json/server.js/site.config.json/the search index is exactly that.

| # | Criterion | Proof |
|---|---|---|
| N1 | The scaffold's runtime plumbing (`package.json`, `server.js`, `site.config.json`, the search index dir) lives under `vhost/`, not the site root; `server.js` correctly resolves the real site root as one directory up from its own location | `test/create-site/generate-site.test.ts`, `e2e/create-site-packaging.check.ts` (real npm pack/install/boot against the new layout) |
| N2 | `drafts/` and `redirects.json` live nested inside `content/`, not as siblings of it; the four bugs this nesting would otherwise introduce are each explicitly proven fixed, not just "it works" | `test/routes/content.test.ts` (drafts/redirects.json rejected at the generic content read/delete routes), `test/services/content-read.test.ts`/`test/services/migration-runner.test.ts` (no duplicate/mislabeled entries from the inclusion-based walk), `test/services/checkpoint.test.ts` (a real commit fires against the nested path, not a hardcoded stale one) |
| N3 | Menus are directly writable (`PUT /v1/menus/:name`) with an immediate commit and no draft state, reversing Group L's original draft-then-publish design for menus; real optimistic-concurrency protection is preserved, not dropped | `test/services/manage-menus.test.ts`, `test/routes/menus.test.ts` (including the concurrent-PUT-resolves-to-one-success proof) |
| N4 | GET/DELETE/move for `menus/` paths are untouched, still generic through the existing `/v1/content` routes - only the write path changed | `test/routes/menus.test.ts :: GET /v1/content/menus/:name and DELETE /v1/content/menus/:name still work through the generic content routes, unchanged` |

Design notes:

- **Two rounds of research plus a Plan-agent design review, all before code was written**, found four real bugs the content-nesting would introduce if unhandled: `GET`/`DELETE /v1/content/:path` would leak/mishandle `drafts/`/`redirects.json` through the generic content routes (fixed with an explicit reserved-path rejection); `listContent`/`migration-runner.ts` would double-walk once a broad `contentRoot` scan started descending into `content/drafts/` (fixed architecturally with an inclusion-based rewrite - three named walks, pages/posts/menus, rather than an exclusion list that would need remembering to update later); `redirects.json` would get misvalidated as a page by the migration runner (solved by the same inclusion-based fix, for free); and, most seriously, `checkpoint.ts`'s periodic draft-safety-net commit had a **hardcoded `'drafts'` pathspec never derived from `config.draftsRoot`** - would have silently stopped committing drafts with zero error output once `draftsRoot` moved. Fixed by deriving the pathspec from `config.draftsRoot` via `relative()`.
- **`site.config.json` moving into `vhost/` was a follow-on decision, not part of the original ask** - initially kept at the site root on the theory that auth tokens might need to outlive any one "vhost" if the term implied multiple vhosts sharing one content tree; once the user clarified `vhost` was chosen for its real hosting meaning (one vhost per site, not shared), that reasoning inverted - tokens/rate-limits/IP-allowlist are exactly the kind of access-control/serving parameters a real vhost config traditionally holds, so it belongs there. `loadServerConfig`/`bootSite`/`startServer` all still resolve off the one `siteRoot` argument with no new parameter threading; only the internal `configPath` construction changed.
- **Menus keep real ETag-checked conflict detection, not redirects' entry-level create/update semantics** - a design review caught that a naive "just write the whole file and commit" endpoint (copying `manage-redirects.ts`'s shape wholesale) would silently drop the optimistic-concurrency protection pages already have via drafts' `If-Match`/409. `manage-menus.ts`'s `saveMenu` is modelled on **two** precedents combined: `drafts.ts`'s `saveDraftJob` for the ETag comparison happening *inside* the queued job (a route-layer check-then-enqueue has a real, empirically-verified TOCTOU gap - Group E), and `manage-redirects.ts`'s immediate-`commitPaths`-after-write shape (no draft state).
- **A real bug caught while testing, not just theorised**: `menusRoot` is optional, like `postsRoot` (a site that has never had a menu has no `content/menus/` directory at all). `sanitisePath` unconditionally realpaths its root argument, so creating the very first menu ever would have crashed with a raw `ENOENT` instead of just creating the directory. Fixed by `mkdirSync(config.menusRoot, { recursive: true })` before resolving the write path in `saveMenuJob`.
- **`PUT /v1/menus/:name`'s body is wrapped (`{ content, message, author }`), not raw menu content the way `PUT /v1/drafts/:path` is** - unlike a draft save, this commits immediately, so it needs the same message/author metadata every other commit-creating write in this API already takes in its body (redirects, publish, delete, move). An early draft used custom headers for this instead; caught and corrected before landing, since it would have been a new, inconsistent convention for no reason.
- **GET/DELETE/move for `menus/` paths were deliberately left untouched** - they already work generically through `/v1/content` (confirmed by research before any code was written: neither `drafts.ts`, `publish.ts`, `content.ts`, nor `batch.ts` has any menu-specific branching to remove), so only the write path needed to change.

`better-sqlite3` as an optional SQLite driver.
